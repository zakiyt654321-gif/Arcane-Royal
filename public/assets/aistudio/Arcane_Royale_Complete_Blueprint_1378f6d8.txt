## THE STAT SYSTEM & MATH (CRITICAL)
There are 4 stats: PWR, FOC, AGI, VIT. 
Every fighter has a total stat budget of exactly 40 points. 
The math scales directly off these stats using this exact formula:
- **Max HP:** `80 + (VIT * 5)` (If VIT is 12, HP is 140).
- **Max Mana:** `80 + (FOC * 2)` (If FOC is 16, Mana is 112).
- **Mana Regen / Second:** `4 + (FOC * 0.25)` (If FOC is 16, regen is 8 per sec).
- **Move Speed:** `3 + (AGI * 0.2)` (Pixels per frame at 60fps).
- **Sword Damage:** `10 * (PWR / 10)` (If PWR is 16, damage is 16).
- **Spell Damage:** `15 * (FOC / 10)` (If FOC is 4, damage is 6).

## PART 3: THE BOT AI (STATE MACHINE) & THE STORM
### THE BOT AI BRAIN
The game features 7 AI bots. They must not just stand still or run at the player. They must use a "Finite State Machine" (FSM). At any given frame, a bot is in exactly one of these 6 states:
#### 1. STATE: IDLE
- **Trigger:** Spawn, or no enemies nearby.
- **Action:** The bot stands still or moves very slightly. It scans the area.
- **Exit Condition:** If an enemy (player or other bot) comes within 600 pixels, switch to CHASE or FLEE based on health.
#### 2. STATE: WANDER
- **Trigger:** No enemies nearby for 5 seconds.
- **Action:** The bot picks a random direction and walks slowly (50% speed). This makes the map feel alive.
- **Exit Condition:** Enemy spotted within 600 pixels, or Storm forces them to move.
#### 3. STATE: CHASE
- **Trigger:** Enemy spotted and bot has > 50% HP.
- **Action:** The bot moves directly towards the enemy at full speed. 
- **Exit Condition:** Distance to enemy < 150 pixels (switch to ATTACK), or HP drops below 50% (switch to FLEE).
#### 4. STATE: ATTACK
- **Trigger:** Distance to enemy is between 50 and 150 pixels.
- **Action:** 
  - If Mana > 20, cast Spell.
  - If Distance < 50 pixels, swing Sword.
  - If Enemy casts a spell at the bot, and bot has Mana > 12, use Dash to dodge sideways.
- **Exit Condition:** Enemy moves out of range (switch to CHASE), or HP drops below 50% (switch to FLEE).
#### 5. STATE: FLEE
- **Trigger:** HP drops below 50%, or the Storm is closing in on the bot.
- **Action:** The bot turns away from the enemy and runs towards the center of the safe zone. It will use Dash to escape if Mana allows.
- **Exit Condition:** HP is somehow restored (impossible in v1) or Enemy stops chasing. If cornered, it will switch to ATTACK (desperation).
#### 6. STATE: DEAD
- **Trigger:** HP <= 0.
- **Action:** Stop all movement. Draw a grey "X" on the ground. The match loop checks if this was the last bot alive.
### BOT BEHAVIOR BY FIGHTER TYPE
Even though all bots use the same state machine, their stats change how they act:
- **Berserker Bots:** They prefer CHASE and ATTACK. Their FLEE state only triggers when HP < 30% (because they have high HP). They rush in and use Crimson Cleave when the enemy is right in front of them.
- **Tidecaller Bots:** They prefer ATTACK from max range (150 pixels). They will actively back away while shooting. If an enemy gets closer than 50 pixels, they Dash backwards.
- **Shadow Bots:** They are erratic. They dash frequently to close gaps, use Phantom Cut to teleport through enemies, and flee quickly when low.
### PATHFINDING & OBSTACLES (V1)
- **No Complex Mazes:** V1 has no walls or complex obstacles. The arena is an open field.
- **Wall Avoidance:** If a bot's movement vector takes it outside the 3000x3000 arena bounds, it hits an invisible wall and slides along it.
- **Separation:** Bots must not stack on top of each other. If two bots are within 60 pixels of each other, they push away from each other slightly (this prevents a "clump" of bots).

### CAMERA AND SCREEN SHAKE
- The camera follows the player, but does not snap instantly. It uses "Lerp" (Linear Interpolation) to smoothly follow the player with a slight delay. (e.g., `cameraX += (playerX - cameraX) * 0.1;`).
- If the player or a bot uses a heavy attack (like Crimson Cleave or Tidal Edge), the camera shakes. 
- **Screen Shake Logic:** The camera's `x` and `y` coordinates are offset by a random number between `-10` and `+10` for 0.3 seconds, then return to normal.
### PERFORMANCE AND MEMORY MANAGEMENT (CRITICAL FOR GALAXY A06)
- **No Object Creation in the Loop:** Do not use `new Object()`, `new Array()`, or `[ ]` inside the `update()` or `render()` functions. Pre-allocate all variables at the top of the file. Reuse them.
- **Canvas Clearing:** Use `ctx.clearRect(0, 0, canvas.width, canvas.height)` at the beginning of every frame.
- **Frame Rate Independence:** The game loop must calculate `deltaTime` (the time between frames). 
  - If a player moves at 5 pixels per frame at 60fps, they move 300 pixels per second.
  - Since `deltaTime` is calculated in seconds (see Part 15) and `speed` is defined in pixels per frame at 60fps, multiply `deltaTime` by 60 to normalize movement across frame rates. The math must be: `player.x += speed * (deltaTime * 60);`. This ensures that if the phone drops to 30fps, the player moves the exact same distance, just in fewer, larger steps.
## PART 5: THE CORE ENGINE ARCHITECTURE & CLASSES
### FILE ORGANIZATION
To keep the codebase clean and prevent the AI from writing 5,000 lines of spaghetti code, we strictly divide the logic into two JavaScript files:
1. `core.js`: Contains the Game Loop, Input Handler (Touch/Keyboard), Math Utilities, Camera logic, and the base Entity class.
2. `game.js`: Contains the specific Arcane Royale rules, Player initialization, Bot AI logic, Storm logic, and Character stats.
### THE ENTITY CLASS (Base Class)
Every moving object in the game (Player and Bots) inherits from a base `Entity` class. This prevents writing the same movement and collision code twice.
- **Properties:** x, y, radius, hp, maxHp, mana, maxMana, speed, faction (Player or Bot), state (Idle, Chasing, Dead), facingAngle (in radians).
- **Methods:** 
  - `update(deltaTime)`: Applies movement, handles knockback, regenerates mana.
  - `takeDamage(amount)`: Reduces HP, triggers screen shake if it's the player, checks for death.
  - `draw(ctx)`: Renders the entity on the canvas (a colored circle or square).
  - `useSword()`, `useSpell()`, `useDash()`, `useArt()`: Methods that are overwritten by specific character logic.
### THE PROJECTILE CLASS
Spells and some Sword Arts (like Tidal Edge) spawn projectiles.
- **Properties:** x, y, radius, vx (velocity x), vy (velocity y), damage, owner, lifespan, type, pierce.
- **Methods:**
  - `update(deltaTime)`: Moves the projectile forward based on vx and vy. Decreases lifespan. Checks map boundaries.
  - `draw(ctx)`: Renders a colored circle or rectangle.
- **Collision:** In the game loop, we check if any Projectile's circle intersects with any Entity's circle. If yes, apply damage, destroy projectile (unless pierce > 0).
### THE GAME STATE MANAGER
A single global object called `Game` will manage the flow of the match.
- `Game.state`: Can be "MENU", "PLAYING", "GAMEOVER".
- `Game.time`: Tracks the 3-minute match timer.
- `Game.aliveCount`: Tracks how many entities are still alive.
- `Game.entities`: An array containing the 1 Player and 7 Bot objects.
- `Game.projectiles`: An array containing all active spells/waves.
### PERFORMANCE: OBJECT POOLING (CRITICAL)
The Samsung A06 has limited RAM. We cannot constantly create and destroy Projectile objects.
- Implement a Projectile Pool. 
- At the start of the game, create 50 empty projectile objects and push them into an array.
- When a spell is cast, find an "inactive" projectile from the pool, set its coordinates to the player, and set it to "active".
- When it hits a wall or enemy, set it to "inactive" instead of deleting it.
- This ensures garbage collection never stutters the game loop.
## PART 6: COLLISION & PHYSICS MATH
### THE MATH OF MOVEMENT
- **Normalization:** If a player inputs a diagonal movement (e.g., dragging the joystick to the top-right), the speed must not increase. We calculate the distance `dx` and `dy`. If the distance is greater than the max speed, we scale `dx` and `dy` down so the total vector length equals the max speed.
- **Facing Angle:** The player's `facingAngle` is calculated using `Math.atan2(dy, dx)`. This angle is used to determine where projectiles spawn and which way the sword swings.
- **Knockback:** When knockback occurs, we apply a velocity (e.g., `vx = 15`). Every frame, `vx` is multiplied by 0.9 (friction). When `vx` drops below 0.1, knockback ends.
### COLLISION DETECTION: CIRCLE TO CIRCLE
The most important math in the game. Used for Player-to-Bot collision and Projectile-to-Bot collision.
- **Formula:** 
  - `dx = circle1.x - circle2.x`
  - `dy = circle1.y - circle2.y`
  - `distance = Math.sqrt((dx * dx) + (dy * dy))`
  - If `distance < circle1.radius + circle2.radius`, a collision has occurred.
- *Optimization:* Do not use `Math.sqrt` on every frame for every entity. Instead, compare the squared distance: `if (dx*dx + dy*dy < (r1+r2)*(r1+r2))`.
### COLLISION DETECTION: RECTANGLE TO CIRCLE (SWORD)
The basic sword attack uses a rectangular hitbox projected in front of the player.
- **Logic:**
  - Center of the rectangle is `player.x + (Math.cos(facingAngle) * 50)`.
  - The rectangle has a width of 80 and a height of 40.
  - We check if the distance from the enemy's circle center to the closest point on the rectangle is less than the enemy's radius.
### COLLISION DETECTION: THE 180-DEGREE ARC (CRIMSON CLEAVE)
This is a cone-shaped attack. It hits every enemy in front of the Berserker.
- **Logic:**
  1. Check if the enemy is within a 150-pixel radius of the Berserker.
  2. Calculate the angle between the Berserker and the enemy.
  3. Check if that angle is within 90 degrees (1.57 radians) of the Berserker's `facingAngle`.
  4. If both are true, the enemy is hit.
### COLLISION DETECTION: LINE INTERSECTION (PHANTOM CUT)
The Shadow teleports forward. It must hit enemies in the path of the teleport.
- **Logic:** Draw a line from the start point to the end point. Check if any enemy's circle intersects with this line. If yes, apply damage.

## PART 8: GAME JUICE, VISUAL EFFECTS & AUDIO
### THE CONCEPT OF "JUICE"
"Juice" is the instant, satisfying feedback a player gets when they do something. A sword swing shouldn't just reduce a number; it should feel like it has impact. Since we are using simple 2D shapes, the juice must come from timing, screen effects, and particles.
### HIT FLASH & COLOR SHIFT
- When an entity takes damage, they must flash a bright white color for exactly 0.1 seconds.
- **Implementation:** The Entity class has a `hitFlashTimer` variable. When `takeDamage()` is called, set `hitFlashTimer = 0.1`. In the `draw()` function, if `hitFlashTimer > 0`, draw the entity as a white circle instead of its normal color. Reduce the timer by `deltaTime`.
### PARTICLE EFFECTS (NO IMAGES)
We will use simple math to spawn particles (small circles) that fly outward from a point and fade away. 
- **Blood/Sparks:** When an enemy is hit by a sword, spawn 5-10 small circles (red or yellow) that scatter outward.
- **Particle Object Pool:** Just like projectiles, we pre-allocate an array of 100 particle objects. 
- **Particle Logic:** Each particle has `x`, `y`, `vx`, `vy`, `alpha` (opacity), and `lifespan`. Every frame, `x += vx`, `y += vy`, `alpha -= 0.05`. If `alpha <= 0`, the particle becomes inactive.
### SCREEN SHAKE
- We want the camera to shake on heavy impacts.
- **Implementation:** Maintain a global variable `screenShakeAmount = 0`. When a heavy attack lands, set it to 15 (pixels).
- In the camera rendering function, offset the canvas translation by a random number between `-screenShakeAmount` and `+screenShakeAmount`. 
- Every frame, `screenShakeAmount *= 0.9`. This creates a smooth decay back to zero.
### WEB AUDIO API (NO MP3 FILES)
We will not download or load `.mp3` or `.wav` files because they take time to load and can cause lag. Instead, use the browser's built-in `AudioContext` to synthesize retro sound effects.
- **Sword Swing:** A quick "whoosh" (White noise, high frequency, very short duration).
- **Spell Cast:** A "pew" or "zap" (Oscillator changing frequency quickly).
- **Hit Damage:** A low "thud" (Low frequency sine wave, short duration).
- **Rule:** All audio must be triggered by a user interaction first (tapping "Start Game") due to browser autoplay restrictions. Keep audio volume at 50% by default.
## PART 9: THE STORM & MATCH DYNAMICS (DEEP DIVE)
### THE STORM LOGIC
The storm is not just a visual effect; it is the ultimate rule enforcer. It dictates the pace of the game.
- **Data Structure:** The storm has a `currentRadius`, `currentCenterX`, `currentCenterY`, `targetRadius`, `targetCenterX`, `targetCenterY`, and `phase` (1 to 4).
- **Interpolation:** When a phase changes, the storm does not snap to the new size. Over 15 seconds, it linearly moves its center and shrinks its radius to the new target. (e.g., `currentRadius -= (currentRadius - targetRadius) * speed * deltaTime`).
### DAMAGE TICKING
- The storm must apply damage exactly 1 time per second. 
- **Implementation:** Maintain a global `stormDamageTimer`. Add `deltaTime` to it. When it exceeds 1.0, loop through all entities. If an entity's distance from the storm's center is greater than `currentRadius`, subtract 5 HP, and reset the timer to 0.
- This prevents the storm from dealing 60 damage in a single second if the frame rate drops.
### BOT STORM AWARENESS
- Bots are not smart enough to survive the storm unless we tell them to. 
- **Rule:** If a bot is outside the safe zone, its State Machine **must** override its current state (even if it's fighting) and switch to `STATE: FLEE`. 
- In the FLEE state, the bot calculates the fastest path to the center of the safe circle and runs at max speed. It will ignore enemies until it is safely inside the circle.
### MATCH END AND PLACEMENT
- The game must track the order of death. 
- When an entity dies, its `placement` is equal to the current `aliveCount`. (e.g., if 5 people are alive and you die, you get 5th place).
- If the player dies, the game enters `GAMEOVER` state. The camera stops following the player and pans to the center of the storm to show the final fight, while a UI overlay displays "YOU DIED - PLACEMENT: #5".
- If the player wins, display "VICTORY ROYALE" with their name.
## PART 10: BOT AI ADVANCED TACTICS & PATHFINDING
### LINE OF SIGHT (LOS)
- A bot cannot shoot a spell through a wall or obstacle. (Note: v1 has no walls, but we must implement the logic for future-proofing).
- **Implementation:** Draw an invisible line from the bot to the enemy. Check if this line intersects with any "wall" objects. If it does, the bot cannot see the enemy and stays in `STATE: WANDER`.
### BOT DODGING LOGIC
- Bots should not just stand there and get hit by spells. 
- If a projectile is moving towards a bot, and the bot has Mana > 12, the bot should trigger `useDash()`.
- **Math:** Calculate the trajectory of the projectile. If the projectile will intersect with the bot's current position in the next 0.5 seconds, the bot dashes perpendicular to the projectile's path.
### KITING & RANGE MANAGEMENT (TIDECALLER BOTS)
- Tidecaller bots want to stay exactly 150 pixels away from their target.
- **Logic:**
  - If distance > 150: Move towards the enemy (Chase).
  - If distance < 100: Move away from the enemy (Flee).
  - If distance is between 100 and 150: Stop moving and shoot spells.
### AGGRESSION TIMERS
- If bots are in `STATE: WANDER` for too long, they get bored. 
- Every 10 seconds of wandering, a bot will "ping" the map for the nearest enemy and run towards them (even if they are far away). This ensures the match doesn't end in a 3-minute standoff between two scared bots.
### BOT MANA MANAGEMENT
- Bots must not spam spells until they are out of mana and defenseless.
- **Rule:** A bot will only cast a spell if `currentMana > 30`. They save the remaining 30 mana for Dashing (12 mana) or their ART (45 mana).

### THE 3000x3000 ARENA

## PART 14: PROJECTILE POOLING (MEMORY MANAGEMENT)
### THE PROBLEM WITH LAG
If you create a new JavaScript object every time a player casts a spell (e.g., `let spell = {x: 100, y: 100...}`), the phone's browser has to allocate memory. When the spell hits a wall, the browser deletes the memory. If 8 players cast spells rapidly, the browser's "Garbage Collector" will kick in, causing a 0.5-second freeze. On the Galaxy A06, this is a death sentence for a fast-paced game.
### THE SOLUTION: OBJECT POOLING
We create all the objects *once* at the start of the game, and recycle them.
**Step 1: The Setup**
```javascript
const MAX_PROJECTILES = 50;
const projectilePool = [];
for (let i = 0; i < MAX_PROJECTILES; i++) {
    projectilePool.push({
        active: false,
        x: 0, y: 0,
        vx: 0, vy: 0,
        radius: 10,
        damage: 0,
        owner: null,
        lifespan: 0,
        type: 'NORMAL',
        pierce: 0
    });
}
function spawnProjectile(x, y, angle, speed, damage, owner, type = 'NORMAL', pierce = 0) {
    for (let i = 0; i < projectilePool.length; i++) {
        if (projectilePool[i].active === false) {
            projectilePool[i].active = true;
            projectilePool[i].x = x;
            projectilePool[i].y = y;
            projectilePool[i].vx = Math.cos(angle) * speed;
            projectilePool[i].vy = Math.sin(angle) * speed;
            projectilePool[i].damage = damage;
            projectilePool[i].owner = owner;
            projectilePool[i].lifespan = 2.0; // 2 seconds
            projectilePool[i].type = type;
            projectilePool[i].pierce = pierce;
            return;
        }
    }
}
```
## PART 15: THE GAME LOOP & DELTATIME
### FRAME RATE INDEPENDENCE
A phone running at 60fps and a phone running at 30fps must play the game at the exact same speed. We achieve this by calculating `deltaTime` (the time it took to render the last frame).
### THE GAME LOOP CODE
```javascript
let lastTime = performance.now();
function gameLoop(currentTime) {
    // 1. Calculate Delta Time (in seconds)
    let deltaTime = (currentTime - lastTime) / 1000;
    lastTime = currentTime;
    // 2. Cap Delta Time to prevent teleporting
    // If the phone lags for 1 second, we don't want the player to move 1000 pixels instantly.
    if (deltaTime > 0.1) {
        deltaTime = 0.1;
    }
    // 3. Update Logic
    if (Game.state === "PLAYING") {
        updateEntities(deltaTime);
        updateProjectiles(deltaTime);
        updateStorm(deltaTime);
        checkCollisions();
    }
    // 4. Draw Everything
    renderCanvas();
    // 5. Request next frame
    requestAnimationFrame(gameLoop);
}
```

## PART 22: THE AUDIO ENGINE (WEB AUDIO API)
### ZERO-LATENCY SOUND
Loading MP3s causes lag. We synthesize sound using the browser's native AudioContext.
const AudioEngine = {
    ctx: new (window.AudioContext || window.webkitAudioContext)(),
    playTone: function(frequency, type, duration, volume) {
        if (this.ctx.state === 'suspended') this.ctx.resume();
        let osc = this.ctx.createOscillator();
        let gain = this.ctx.createGain();
        osc.type = type;
        osc.frequency.setValueAtTime(frequency, this.ctx.currentTime);
        gain.gain.setValueAtTime(volume, this.ctx.currentTime);
        gain.gain.exponentialRampToValueAtTime(0.01, this.ctx.currentTime + duration);
        osc.connect(gain);
        gain.connect(this.ctx.destination);
        osc.start();
        osc.stop(this.ctx.currentTime + duration);
    }
};

## PART 25: ADVANCED BOT STEERING & OBSTACLE AVOIDANCE
### STEERING BEHAVIORS (NO A* PATHFINDING)
A* pathfinding requires a grid and is heavy on mobile CPUs. Instead, we use "Steering Behaviors" (Craig Reynolds' algorithm). Bots calculate a vector for their target, and a separate vector to avoid obstacles, then add them together.
### THE AVOIDANCE VECTOR
- If a bot detects a wall or obstacle directly in front of its path, it casts a "feeler" ray 50 pixels forward.
- If the ray hits an obstacle, the bot generates a perpendicular vector (left or right, whichever is closer to the target) and applies a strong steering force in that direction.
### SEPARATION FORCE (PREVENTING CLUMPING)
If three bots chase the player, they will stack on top of each other. We must apply a Separation Force.
- Loop through all bots. If Bot A is within 60 pixels of Bot B, calculate a vector pushing Bot A away from Bot B.
- The closer they are, the stronger the push. 
### WANDER BEHAVIOR
- The bot projects a circle 50 pixels in front of it. 
- A point is placed on the edge of this circle and moved slightly randomly every frame.
- The bot steers towards this point. This creates a natural, organic-looking patrol path rather than robotic straight lines.

## PART 28: JAVASCRIPT OBJECT-ORIENTED & MEMORY TIPS
### PROTOTYPES VS CLASSES
Use ES6 class syntax for readability, but keep methods off the instances to save memory. Do not define functions inside the constructor.
- Bad: this.attack = function() { ... }
- Good: Entity.prototype.attack = function() { ... }
### AVOIDING GARBAGE COLLECTION (GC) STUTTERS
GC runs automatically in Chrome and will freeze the game for a few milliseconds. On a low-end phone, this causes a noticeable stutter. We must minimize memory allocation during the game loop.
- Strings: Do not concatenate strings inside the game loop (e.g., "HP: " + hp). It creates new string objects. Pre-render text or use ctx.fillText(hp, x, y) with a static label.
- Arrays: Use pre-allocated arrays and maintain an activeCount. Do not use .filter() or .map() in the game loop, as they create new arrays. Use a for loop and set variables to null when done.
### CACHING CANVAS PATHS
If you are drawing a complex shape (like the jagged edge of the storm circle), draw it once to an offscreen canvas, and then draw that image in the main loop. Do not recalculate complex paths 60 times a second.

## PART 32: ADVANCED PROJECTILE MATH
### HOMING PROJECTILES (FUTURE PROOFING)
If we ever add a homing missile, the math is:
- Calculate the angle between the projectile and the target.
- Rotate the projectile's velocity vector towards that angle by a small amount each frame (e.g., 0.05 radians).
### PROJECTILE LIFESPAN AND DISTANCE
- Projectiles should have a maximum range, not just a lifespan. 
- Store originX and originY on the projectile when it spawns.
- Every frame, check: Math.hypot(this.x - this.originX, this.y - this.originY). If this distance > maxRange (e.g., 600 pixels), deactivate it.
- This prevents spells from flying across the entire 3000x3000 map.
### WALL COLLISION (RAYCASTING)
When a projectile moves, it might skip through a thin wall if it moves too fast (tunneling).
- To fix this, check the line segment from the projectile's previous position to its current position against the wall.
- If the line intersects the wall, spawn the impact particle at the intersection point, not the projectile's current point.
## PART 33: ANIMATION & INTERPOLATION (LERP)
### WHAT IS LERP?
Linear Interpolation. It's the mathematical way to smoothly transition from Point A to Point B over time. It is the secret to making games feel "smooth" instead of "choppy."
### CAMERA LERP
The camera should never snap to the player instantly. It should follow with a slight delay.
- Formula: camera.x = camera.x + (player.x - camera.x) * cameraSpeed * deltaTime;
- cameraSpeed is usually around 5.0 to 8.0.
- If the player dashes, the camera will smoothly catch up, creating a great sense of speed.
### VISUAL EFFECTS LERP
- When a player dies, they shouldn't just disappear. They should scale down and fade out.
- Store an entity.alpha value (starts at 1.0). On death, entity.alpha -= deltaTime.
- Apply CTX.globalAlpha = entity.alpha; before drawing the dying entity.
### HEALTH BAR LERP
- When the player takes damage, the red HP bar shouldn't instantly snap to the new value. It should drain smoothly.
- Keep a displayHp variable. Every frame: displayHp += (realHp - displayHp) * 0.1.
- Draw the bar using displayHp, not realHp.
## PART 34: THE FINITE STATE MACHINE (FSM) DESIGN
### WHY FSM?
If we just use a bunch of if/else statements for the bots, the code becomes a tangled mess. A Finite State Machine locks a bot into exactly one state at a time, making it predictable and bug-free.
### THE FSM STRUCTURE
Every bot has a this.state property.
- Possible states: "IDLE", "WANDER", "CHASE", "ATTACK", "FLEE", "DEAD".
### STATE TRANSITIONS
Inside the bot's update loop, we evaluate the environment to see if the state should change.
- if (this.hp < maxHp * 0.5 && this.state !== "FLEE") { this.state = "FLEE"; }
- if (this.state === "CHASE" && distanceToEnemy < 100) { this.state = "ATTACK"; }
### THE ATTACK STATE DETAIL
When in ATTACK state:
- The bot stops moving (velocity = 0).
- The bot calculates the angle to the enemy.
- If the bot has Mana, it casts a spell.
- If the enemy is extremely close, it swings its sword.
- If the enemy runs away, it switches back to CHASE.
## PART 35: MOBILE OPTIMIZATION & BATTERY LIFE
### THE SAMSUNG A06 TARGET
The Galaxy A06 has a MediaTek Helio G85. It is a capable budget chip, but it will throttle (slow down) if the phone gets hot. We must optimize to prevent thermal throttling.
### CANVAS RESOLUTION SCALING
- Do not render the game at 4K resolution. It will melt the battery.
- Set the canvas width and height to match the window.innerWidth and window.innerHeight.
- In the CSS, stretch the canvas to 100% width and height. The browser will handle the scaling automatically.
### BACKGROUND TAB PAUSING
- If the player minimizes Chrome or locks their phone, the game loop must pause.
- Listen for the visibilitychange event on the document.
- if (document.hidden) { Game.state = "PAUSED"; } else { Game.state = "PLAYING"; lastTime = performance.now(); }
- This prevents the player from returning to the game and finding they died to the storm while the app was in the background.
